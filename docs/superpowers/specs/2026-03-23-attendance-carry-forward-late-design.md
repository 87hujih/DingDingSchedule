# Attendance Carry-Forward Late Design

## 背景

当前连续节次顺延逻辑位于 `AttendanceRecordService.applyCarryForward`。
它只会把“上一节已记入 `OnTimeIDs` 的用户”顺延到当前节的 `on_time`，
不会把上一节迟到但已完成打卡的用户顺延到下一节。

用户确认的新目标行为是：

1. 上一节正常打卡的用户继续可以顺延到当前节
2. 上一节迟到打卡的用户也可以顺延到当前节
3. 顺延后的落点仍然是当前节 `on_time`
4. 除此之外，现有考勤统计、优先级、落库结构和接口行为全部保持不变

## 目标

在不改变现有统计模型的前提下，扩展连续节次顺延来源：

- 当前节的顺延来源从“上一节 `on_time`”扩展为“上一节 `on_time + late`”
- 当前节的顺延结果仍然只写入当前节 `on_time`
- 不新增配置项，不新增字段，不修改迟到与未到的其它判定逻辑

## 非目标

- 不改变上一节本身的迟到结果
- 不把顺延结果记入当前节 `late`
- 不改变 `lateDeadline`、`finalizeAt`、`not_arrived`、`leave`、`rest_day`、`has_course` 的计算方式
- 不调整群推送、排行、分析统计或人工代签逻辑
- 不修改数据库表结构或快照格式

## 方案选择

### 方案 A：直接在 `applyCarryForward` 中把 `LateIDs` 拼进现有逻辑

优点：

- 改动最小
- 实现最快

缺点：

- `applyCarryForward` 会继续承担 JSON 解析与顺延决策两类职责
- 后续若再调整“哪些状态可顺延”，可读性会继续下降

### 方案 B：新增“可顺延来源”辅助函数

做法：

- 保留 `applyCarryForward` 的入口、调用点和最终落点不变
- 新增一个小的 helper，专门从上一节快照中提取“可顺延用户”
- helper 同时解析 `OnTimeIDs` 和 `LateIDs`，按用户 ID 去重后返回

优点：

- 外部行为改动最小
- 代码职责更清晰
- 便于用测试锁定“顺延来源”这一个变化点

缺点：

- 比方案 A 多一个小 helper

本次采用方案 B。

### 方案 C：增加配置开关控制“迟到是否可顺延”

优点：

- 对线上行为更保守

缺点：

- 用户没有要求新增配置
- 会扩大 blast radius
- 与“其他逻辑保持不变”的目标不一致

不采用。

## 现状逻辑

当前 `applyCarryForward` 的触发条件包括：

1. 当前节必须是第 2 节及以后
2. `max_carry_forward_gap_minutes > 0`
3. 上一节下课到当前节上课的间隔不超过阈值
4. 数据库中存在上一节考勤快照
5. 当前节用户属于 `shouldAttend`
6. 当前节用户尚未进入当前节 `on_time`

在满足这些条件后，系统只会读取上一节 `OnTimeIDs`，
并把这些用户顺延到当前节 `on_time`。

## 新逻辑

新逻辑只改“上一节哪些人可以参与顺延”：

- 旧逻辑：上一节 `OnTimeIDs`
- 新逻辑：上一节 `OnTimeIDs + LateIDs`

其它条件全部不变：

- 仍然要求连续节次间隔不超过阈值
- 仍然要求用户属于当前节 `shouldAttend`
- 仍然要求当前节该用户尚未有 `on_time`
- 仍然只把结果追加到当前节 `on_time`

## 详细行为定义

### 顺延来源

helper 从上一节 `attendance_records` 提取两类用户：

- `OnTimeIDs`
- `LateIDs`

提取规则：

- 解析两类 JSON
- 以用户 ID 为唯一键去重
- 若同一用户同时出现在两类来源里，只保留一份

### 顺延落点

命中顺延条件的用户统一追加到当前节 `on_time`。

保留当前实现的行为：

- 使用上一节保存的 `check_time` 作为顺延后的 `check_time`
- 不生成新的迟到状态
- 不单独打“顺延”标签

### 与当前节实时打卡的关系

若用户当前节已经有实时正常打卡并进入 `on_time`，顺延逻辑不重复追加。

若用户当前节当前尚未进入 `on_time`，但上一节属于可顺延来源，则会被补入当前节 `on_time`。

### 与其它分类的关系

顺延不会绕过现有 `shouldAttend` 过滤。

因此以下用户仍不会因为顺延而进入当前节 `on_time`：

- 当前节不在 `shouldAttend` 的用户
- 当前节有课用户
- 当前节休息日用户
- 当前节已被分类到不应出勤集合的用户

## 代码边界

只修改以下文件：

- `internal/service/attendance_record_service.go`
- `internal/service/attendance_record_service_test.go`

实现边界：

- `applyCarryForward` 保持为唯一顺延入口
- 新增一个内部 helper 收口上一节可顺延来源
- 不调整 `getOnTimeUsers`、`FinalizeAttendanceRecord`、`QueryStats`、排行与快照序列化结构

## 风险与约束

### 1. 同一用户被重复追加

上一节 `OnTimeIDs` 与 `LateIDs` 理论上不应重复，但实现仍需按用户 ID 去重，
避免脏数据导致当前节 `on_time` 重复。

### 2. 误把不满足顺延条件的用户带入当前节

helper 只负责提取上一节的“可顺延来源”，
真正是否顺延仍由 `applyCarryForward` 里的现有条件决定。
不能因为 helper 改动而绕过 `shouldAttend` 和“当前节尚未 on_time”的检查。

### 3. 影响既有统计口径

本次不调整当前节 `late`、`not_arrived` 的生成规则，
只改变当前节 `on_time` 的补入来源。
因此需要补回归测试，确保其它分类结果未被连带改动。

## 测试策略

至少覆盖以下场景：

1. 上一节正常打卡用户仍然可以顺延到当前节 `on_time`
2. 上一节迟到用户在其它顺延条件满足时，也会进入当前节 `on_time`
3. 上一节迟到用户若当前节不属于 `shouldAttend`，不会被顺延
4. 当前节该用户已在 `on_time` 时，不会重复追加
5. 原有实时详情和最终结算相关测试继续通过，证明其它统计逻辑未被带偏

## 验证计划

实现阶段应按 TDD 执行：

1. 先新增“上一节迟到也能顺延”的失败测试
2. 运行该测试，确认在改代码前失败
3. 以最小改动实现 helper 与顺延来源扩展
4. 重新运行新增测试和现有顺延/详情/最终结算测试

## 结论

本次改动应被严格限制为：

- 顺延来源从“上一节正常打卡”扩展到“上一节正常打卡 + 上一节迟到打卡”

除此之外，所有现有统计规则、接口结构和快照格式保持不变。
