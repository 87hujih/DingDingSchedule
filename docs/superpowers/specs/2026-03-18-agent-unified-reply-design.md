# Agent 统一回复编排与超时治理设计

## 目标
在不改变 Agent 业务职责边界的前提下，统一群聊与私聊的回复编排模型，修复当前 LLM 二轮调用被底层 50 秒 HTTP 超时提前截断的问题，同时补齐 DingTalk Stream 连接退避和生产日志可观测性。

## 背景
- 当前群聊已经具备异步处理、慢查询提示和主动推送兜底能力。
- 当前私聊仍然依赖同步 `SessionWebhook` 回复，长尾请求容易直接失败。
- `internal/agent/agent.go` 试图给工具后总结轮次更长的超时预算，但 `internal/agent/client.go` 里的全局 `http.Client.Timeout=50s` 让该设计失效。
- 生产容器把宿主机目录挂载到 `/app/logs`，与非 root 运行用户的权限不匹配，导致文件日志不可写，影响排障。
- DingTalk Stream 连接在单租户超时时会持续报错，但当前对“租户级失败”和“服务级存活”之间的边界不够清晰。

## 范围
- 统一群聊与私聊的回复状态机与编排入口。
- 调整 LLM 调用超时与重试模型。
- 梳理群聊、私聊各自的最终发送通道。
- 明确 DingTalk Stream 的租户级连接退避策略。
- 调整 Docker 生产环境的日志输出策略。

## 非目标
- 不引入消息队列、任务中心或数据库持久化任务表。
- 不改变 Agent 工具集合、提示词和业务语义。
- 不修改现有 `/health` 对外返回契约。
- 不在本设计中扩展新的管理后台页面。

## 设计

### 1. 统一编排层
1. 在 `pkg/dingtalk` 中引入统一的 `ReplyOrchestrator`，负责：
   - 接收消息后进入统一状态机
   - 控制快速响应窗口、总预算和后台继续执行
   - 保证同一请求只产出一个最终结果
   - 记录结构化阶段状态与错误分类
2. `Agent` 继续只负责执行对话，不感知群聊/私聊的发送差异。
3. `StreamClient` 只负责解析钉钉消息、识别会话类型并把请求交给编排器。

### 2. 统一状态机
群聊与私聊统一使用以下状态语义：
- `accepted`：消息已接收，开始处理
- `processing`：超过快速窗口，已向用户发送“正在处理”
- `success`：已发送最终结果
- `failed`：已发送最终失败提示

可选扩展状态：
- `fallback_sent`：最终结果通过备用发送通道发出
- `upstream_timeout`：上游模型或钉钉接口超时
- `tool_failed`：工具执行失败
- `rate_limited`：上游限流

### 3. 通道适配而非通道统一
1. 编排器依赖统一的 `ReplyChannel` 抽象，至少提供：
   - `FastReply`
   - `ProgressReply`
   - `FinalReply`
2. 群聊 sender 负责：
   - 优先走 `SessionWebhook`
   - 失效后主动发回原群会话
3. 私聊 sender 负责：
   - 优先走 `SessionWebhook`
   - 超过同步窗口后通过私聊主动发送能力补发最终结果
4. 因此统一发生在状态机和编排层，不要求群聊与私聊共用同一个发送实现。

### 4. 超时与预算模型
1. 去掉 `LLMClient` 中覆盖整次请求的全局 `http.Client.Timeout`。
2. 由上层 `context` 成为 LLM 请求的唯一总预算来源。
3. 连接类超时保留在 `Transport` 级别，例如拨号、TLS、响应头等待，但不再用一个固定值直接裁掉整次请求。
4. 一次对话分为两级预算：
   - 单轮 LLM 预算
   - 整次对话总预算
5. 推荐预算：
   - 首轮理解：25-35 秒
   - 工具后总结：60-90 秒
   - 群聊总预算：90-120 秒
   - 私聊总预算：与群聊保持一致，采用“先回处理中，再后台补发”的策略

### 5. 重试策略
1. 仅对短暂性错误重试：
   - `429`
   - `5xx`
   - 连接重置、DNS 抖动等网络错误
2. 不对已超出本轮预算的请求重试。
3. 所有重试共享同一个预算池，不重新发放完整超时。
4. 错误分类至少区分：
   - `upstream_timeout`
   - `rate_limited`
   - `network_error`
   - `invalid_response`

### 6. DingTalk Stream 连接策略
1. `StreamClientManager` 以租户为最小连接单元。
2. 单租户连接状态至少区分：
   - `disconnected`
   - `connecting`
   - `connected`
   - `backoff_retry`
3. 某个租户连接 DingTalk 失败时：
   - 记录结构化错误
   - 指数退避重试
   - 不影响其他租户
   - 不影响 HTTP 服务存活
4. `/health` 继续表示进程对外可用；租户级 Stream 细节通过日志或单独内部状态接口观察。

### 7. 生产日志策略
1. Docker 生产环境以 stdout/stderr 为主日志出口。
2. 继续保留结构化 JSON 日志，便于 `docker logs` 和后续采集。
3. 文件日志在 Docker 生产环境默认关闭或降级为可选项。
4. 如果仍保留文件日志：
   - 启动前必须显式检查目录可写
   - 不可写时要么 fail-fast，要么明确降级到 stdout-only
   - 不允许继续出现“服务正常但文件日志静默失效”的状态

## 预期收益
- 修复当前 LLM 二轮总结阶段被底层 50 秒硬超时提前截断的问题。
- 群聊与私聊对用户表现出一致的“受理、处理中、完成、失败”语义。
- 外部接口变慢时，优先保障体验和成功率，而不是简单延长同步等待。
- 某租户 DingTalk Stream 波动时，不再影响全局可用性判断。
- 生产环境排障可以直接依赖 `docker logs`，不再被文件权限问题阻断。

## 风险与权衡
- 统一编排会引入新的抽象层，但复杂度集中在一处，比继续在 `stream.go` 上叠加分支更可控。
- 私聊主动补发依赖钉钉私聊主动发送能力，接入前需确认当前机器人权限与接口约束。
- 不引入持久化任务队列意味着进程重启时，正在后台执行的回复任务不会恢复。

## 测试
- 为统一编排器增加单元测试，覆盖：
  - 快速窗口内直接返回最终结果
  - 超过快速窗口后先发 `processing`
  - 群聊 `SessionWebhook` 失败后主动补发到原群
  - 私聊超时后通过私聊 sender 补发最终结果
  - 同一请求只发送一次最终结果
- 为 LLM 调用层增加回归测试，覆盖：
  - 工具后总结轮次不会再被固定 50 秒超时提前截断
  - 重试仅消耗同一预算池
- 为 Stream 管理层增加测试，覆盖：
  - 单租户连接失败不影响其他租户
  - 失败后进入退避重试
- 为生产配置或日志初始化增加验证，覆盖：
  - Docker 场景下 stdout 日志正常输出
  - 文件日志不可写时不会静默失败
