## 核心结论

- 这是一个面向教育和培训场景的多租户后端系统。
- 它不是单纯的课表系统，而是把钉钉身份、组织架构、课表、考勤、请假、群推送和 AI 助手串成一条业务链。
- 当前系统同时支持 HTTP API、钉钉 Stream、定时调度和 GoAdmin 后台四条运行入口。
- AI 在当前系统里是增强型入口，不是独立平台；它依赖现有课表、考勤、请假和管理服务提供工具能力。

## 这个系统适合什么场景

当前系统更适合以下场景：

- 教育机构或培训机构的多班级排课
- 基于钉钉组织和身份体系的内部管理
- 需要按节次做实时考勤和最终结算
- 需要把请假审批结果自动纳入考勤判断
- 需要在群聊或单聊里通过自然语言查询课表和考勤

它的重点不是“开放式聊天”，而是“面向教务和考勤业务的查询与管理”。

## 系统有哪些运行入口

当前系统有 4 条主要入口：

### HTTP API

这是业务主入口，面向前端、小程序或 H5 提供接口。

典型能力包括：

- 登录
- 课表查询
- 考勤详情
- 补签
- 学期和作息设置

### DingTalk Stream

这是钉钉事件和聊天消息的入口。

它承担两类事情：

- 接收审批事件，同步请假记录
- 接收聊天消息，交给 AI Agent 处理

### 定时调度

这是自动考勤和最终结算的入口。

它会根据作息配置和节次时间触发：

- 实时统计
- 最终结算
- 推送相关任务

### GoAdmin 后台

这是后台管理和运维入口。

它主要用于：

- 管理租户
- 查看和维护部分基础配置
- 查看后台表和日志

## 典型业务链路

### 课表与考勤链路

1. 管理员导入或维护课表
2. 系统按学期、星期和节次计算当前课程安排
3. 到课节时间后触发考勤统计
4. 用户打卡、请假、休息日等信息共同参与分类
5. 最终结果写入快照并可用于排行、文本生成和 AI 查询

### 请假同步链路

1. 用户在钉钉发起请假审批
2. 系统通过 Stream 收到审批事件
3. 拉取审批详情并解析表单
4. 写入本地请假表
5. 后续考勤统计按时间窗口使用该请假数据

### AI 查询链路

1. 用户在钉钉单聊或群聊发消息
2. 系统把消息交给 Agent
3. Agent 根据问题调用课表、考勤、请假或管理工具
4. 组合工具结果后返回自然语言回答

## AI 在系统里的角色

当前 AI 更像“业务助手入口”，不是独立大模型平台。

它的价值主要在于：

- 用自然语言访问已有业务能力
- 把课表、考勤、请假和管理操作统一成对话入口
- 在群聊场景下减少人工查询成本

因此当前 AI 的基础是已有业务服务，而不是脱离业务单独存在。

## 当前实现边界

- 当前系统主场景是教务、考勤和钉钉集成，不是通用 OA 平台
- 当前 AI 能力以工具调用为主，依赖现有业务数据和权限控制
- 当前后台是 GoAdmin 风格的管理入口，不是专门设计的独立运营后台
