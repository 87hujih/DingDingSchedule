# Schedule Server 核心功能详解

本文档对 Schedule Server 多租户排课考勤管理系统的项目背景与核心功能需求进行深入讲解，帮助开发者和产品人员快速理解系统设计思路。

---

## 一、项目简介详解

### 1.1 项目定位

Schedule Server 是一套面向**教育/培训机构**的 SaaS 化管理系统，核心解决以下痛点：

| 痛点 | 解决方案 |
|------|----------|
| 手工统计考勤效率低、易出错 | 系统自动计算「应到人员」，结合请假数据实时出统计 |
| 课表分散在 Excel/纸质文件中 | 支持 Excel 导入，统一存储、按周查询 |
| 请假审批与考勤脱节 | 深度集成钉钉审批，请假自动扣减考勤 |
| 多校区/多企业数据混杂 | 多租户架构，数据完全隔离 |

### 1.2 多租户架构

系统采用**单数据库多租户（Shared Database, Shared Schema）** 模式：

```
┌─────────────────────────────────────────────────────────────┐
│                        MySQL 数据库                          │
├─────────────────────────────────────────────────────────────┤
│  tenant_id=1 (企业A)  │  tenant_id=2 (企业B)  │  ...        │
│  ├── users           │  ├── users           │              │
│  ├── departments     │  ├── departments     │              │
│  ├── courses         │  ├── courses         │              │
│  └── ...             │  └── ...             │              │
└─────────────────────────────────────────────────────────────┘
```

**隔离机制**：
- 所有业务表均含 `tenant_id` 字段
- GORM 插件自动注入 `WHERE tenant_id = ?` 条件
- JWT Token 中携带 `tenant_id`，中间件自动提取并注入 Context
- 开发者无需手动编写租户过滤逻辑，防止数据泄漏

### 1.3 钉钉深度集成

系统与钉钉开放平台深度集成，涵盖以下能力：

| 能力 | 实现方式 |
|------|----------|
| 单点登录（SSO） | 钉钉免登码 → 换取用户身份 → 签发 JWT |
| 组织架构同步 | 调用钉钉通讯录 API，同步用户/部门 |
| 审批流程集成 | 接收钉钉审批事件回调，同步请假数据 |
| 消息推送（规划中） | 通过工作通知推送考勤异常提醒 |

**认证流程图**：

```
┌──────────┐    ①免登码     ┌──────────────┐
│ 钉钉客户端 │ ───────────> │ Schedule     │
└──────────┘               │ Server       │
      ▲                    └──────┬───────┘
      │                           │
      │                    ②调用钉钉API
      │                    换取用户身份
      │                           │
      │                           ▼
      │                    ┌──────────────┐
      │                    │ 钉钉开放平台  │
      │                    └──────┬───────┘
      │                           │
      │                    ③返回用户信息
      │                           │
      │    ④返回JWT Token         ▼
      └──────────────────── Schedule Server
```

## 二、核心功能需求详解

### 2.1 用户与组织管理

#### 2.1.1 用户模型

```
User
├── id                  # 系统内部ID
├── tenant_id           # 所属租户
├── ding_user_id        # 钉钉用户ID（租户内唯一）
├── name                # 姓名
├── name_pinyin         # 姓名全拼（用于搜索）
├── name_pinyin_abbr    # 姓名拼音首字母
├── phone               # 手机号
├── avatar              # 头像URL
├── role                # 角色（0=普通用户, 1=管理员, 2=超级管理员）
└── status              # 考勤参与状态（0=不参与, 1=参与）
```

#### 2.1.2 角色权限体系

| 角色 | 权限范围 | 典型场景 |
|------|----------|----------|
| 普通用户 (0) | 仅可访问自己的课表、考勤记录 | 教师/学员 |
| 管理员 (1) | 可访问租户内所有数据，执行同步/统计操作 | 教务管理员 |
| 超级管理员 (2) | 预留，用于跨租户管理（暂未启用） | 平台运维 |

**权限校验流程**：

```go
// 中间件层：JWT 认证
JWTAuth() → 提取 user_id, role, tenant_id → 写入 Context

// 中间件层：角色校验
RequireAdmin() → 检查 role >= 1 → 不满足返回 403

// 业务层：数据可见性
VisibleUserScope(viewerID, viewerRole) → 返回可访问的用户ID列表
  - 管理员：无限制（返回空列表表示全部可见）
  - 普通用户：仅返回自己的ID
```

#### 2.1.3 组织同步机制

**部门同步**：
1. 调用钉钉 `/department/list` 递归获取所有部门
2. 本地采用 Upsert 策略（按 `tenant_id + dept_id` 唯一键）
3. 自动标记叶子部门（`is_leaf` 字段）

**用户同步**：
1. 调用钉钉 `/user/listid` 获取用户ID列表
2. 批量调用 `/user/get` 获取详情
3. 自动生成拼音索引（支持中文姓名模糊搜索）
4. 保留本地 `role`、`status` 字段，仅更新钉钉来源字段

### 2.2 课程排班

#### 2.2.1 课程数据模型

```
Course
├── id                  # 课程ID
├── tenant_id           # 租户ID
├── user_id             # 所属用户（教师）
├── semester_id         # 关联学期（可空，兼容历史数据）
├── course_name         # 课程名称
├── teacher             # 授课教师（冗余字段，用于显示）
├── location            # 上课地点
├── day_of_week         # 星期几（1-7，周一到周日）
├── section             # 大节次（1=第1-2节, 2=第3-4节, ...）
└── week_list           # 周次列表（如 "1,2,3,5,8-10"）
```

#### 2.2.2 周次列表格式

周次采用**字符串存储**，支持灵活表达：

| 格式 | 含义 | 示例 |
|------|------|------|
| 单个数字 | 单周 | `"3"` → 第3周 |
| 逗号分隔 | 多个离散周 | `"1,3,5"` → 第1、3、5周 |
| 连字符 | 连续周范围 | `"1-10"` → 第1至10周 |
| 混合 | 组合使用 | `"1-5,8,10-12"` → 第1-5、8、10-12周 |

**解析工具**：`pkg/weekutil` 提供周次字符串解析与校验函数。

#### 2.2.3 课表导入流程

```
┌──────────────┐
│ 用户上传 Excel │
└──────┬───────┘
       │
       ▼
┌──────────────┐     格式校验
│ 文件类型检测   │ ──────────────> 仅支持 .xls / .xlsx
└──────┬───────┘
       │
       ▼
┌──────────────┐     解析单元格
│ Excel 解析    │ ──────────────> 提取课程名、周次、节次等
└──────┬───────┘
       │
       ▼
┌──────────────┐     事务操作
│ 数据入库      │ ──────────────> DELETE 旧数据 + INSERT 新数据
└──────┬───────┘                  （全量替换策略）
       │
       ▼
┌──────────────┐
│ 返回导入数量   │
└──────────────┘
```

**设计决策**：
- 采用**全量替换**而非增量更新，避免数据不一致
- 导入时自动关联当前激活学期
- 空文件/无有效数据时拒绝导入

### 2.3 考勤统计

#### 2.3.1 核心公式

```
应到人员 = 参与考勤的候选人 - 当前时段有课人员

其中：
- 候选人 = status=1 的用户（可按部门过滤）
- 有课人员 = 该用户在「指定周次 + 星期 + 节次」有课程安排
```

#### 2.3.2 时间窗口计算

每个节次对应一个时间窗口，由 `schedule_periods` 表配置：

```
节次1: 08:00 - 09:40
节次2: 10:00 - 11:40
节次3: 14:00 - 15:40
节次4: 16:00 - 17:40
...
```

系统根据「日期 + 节次」计算出精确的时间窗口，用于：
- 判断用户是否有课（课程时间与窗口重叠）
- 判断用户是否请假（请假时间与窗口重叠）

#### 2.3.3 考勤状态分类

| 状态 | 判定条件 |
|------|----------|
| 应到 | 参与考勤 + 该时段无课 |
| 请假 | 有已批准的请假审批，且时间窗口重叠 |
| 正常打卡 | 已在钉钉打卡（需集成，当前预留） |
| 未到 | 应到但未打卡、未请假 |

#### 2.3.4 快照机制

考勤数据支持两种查询模式：

| 模式 | 接口 | 说明 |
|------|------|------|
| 实时计算 | `GET /attendance/record/detail` | 每次请求重新计算 |
| 快照查询 | `GET /attendance/record/snapshot` | 读取数据库已保存记录 |

管理员可通过 `POST /attendance/record/trigger` 手动触发统计并持久化。

### 2.4 请假审批同步

#### 2.4.1 数据模型

```
LeaveApproval
├── id                      # 本地ID
├── tenant_id               # 租户ID
├── process_instance_id     # 钉钉审批实例ID（唯一键）
├── process_code            # 审批模板编码
├── ding_user_id            # 申请人钉钉ID
├── user_id                 # 申请人本地ID
├── user_name               # 申请人姓名（快照）
├── start_at                # 请假开始时间
├── end_at                  # 请假结束时间
├── leave_type              # 请假类型（事假/病假/年假等）
├── reason                  # 请假事由
├── approve_status          # 审批状态（RUNNING/COMPLETED/TERMINATED）
└── result                  # 审批结果（agree/refuse）
```

#### 2.4.2 回调处理流程

```
┌──────────────┐
│ 钉钉审批事件   │
│ 回调推送      │
└──────┬───────┘
       │
       ▼
┌──────────────┐     1. 验签解密
│ 回调接收接口   │ ──────────────> 校验签名 + AES解密
└──────┬───────┘
       │
       ▼
┌──────────────┐     2. 幂等检查
│ 查询已有记录   │ ──────────────> 按 process_instance_id 查询
└──────┬───────┘
       │
       ├─── 存在 ───> UPDATE 更新状态
       │
       └─── 不存在 ──> INSERT 新建记录
              │
              ▼
       ┌──────────────┐
       │ 异步处理      │ ──> 后续业务（通知等）
       └──────────────┘
```

#### 2.4.3 时间重叠检测

判断请假是否影响某节次考勤，采用**半开区间**算法：

```
请假时间: [leave_start, leave_end)
节次时间: [slot_start, slot_end)

重叠条件: leave_start < slot_end AND leave_end > slot_start
```

示例：
- 请假 08:00 - 12:00，节次1 08:00 - 09:40 → **重叠**（计入请假）
- 请假 08:00 - 09:40，节次1 08:00 - 09:40 → **重叠**（计入请假）
- 请假 12:00 - 14:00，节次1 08:00 - 09:40 → **不重叠**（正常考勤）

### 2.5 学期与作息配置

#### 2.5.1 学期管理

```
Semester
├── id              # 学期ID
├── tenant_id       # 租户ID
├── name            # 学期名称（如"2025-2026学年第二学期"）
├── start_date      # 开学日期（第1周周一）
├── total_weeks     # 总周数（默认20）
└── is_active       # 是否当前激活学期
```

**激活学期**：
- 每个租户同一时间仅一个激活学期
- 激活学期用于：
  - 课表导入时的默认关联
  - 周次校验（确保在学期范围内）
  - 计算当前是第几周

**周次计算**：

```go
当前周 = (当前日期 - 开学日期) / 7 + 1

示例：
开学日期 = 2026-02-09（周一）
当前日期 = 2026-02-20（周五）
当前周 = (11天 / 7) + 1 = 2（第2周）
```

#### 2.5.2 作息模式

系统支持两种作息模式：

| 模式 | 标识 | 说明 |
|------|------|------|
| 上学模式 | `school` | 正常教学期间使用 |
| 假期模式 | `holiday` | 寒暑假/节假日使用 |

每种模式可配置不同的作息时间段：

```
上学模式:
  - 第1节: 08:00 - 09:40
  - 第2节: 10:00 - 11:40
  - 第3节: 14:00 - 15:40
  - 第4节: 16:00 - 17:40

假期模式:
  - 第1节: 09:00 - 11:30
  - 第2节: 14:00 - 16:30
```

**模式切换**：
- 管理员通过 `/api/schedule/switch-mode` 接口切换
- 考勤调度器自动使用当前激活模式的时间配置

## 三、技术实现要点

### 3.1 数据一致性保障

| 场景 | 策略 |
|------|------|
| 课表导入 | 事务内 DELETE + INSERT，全量替换 |
| 用户部门同步 | 事务内 DELETE 关联表 + 批量 INSERT |
| 请假回调 | 唯一约束 + Upsert，保证幂等 |

### 3.2 性能优化

| 场景 | 优化手段 |
|------|----------|
| 用户搜索 | 拼音索引 + 数据库 LIKE 查询 |
| 考勤计算 | 预先过滤参与考勤用户，减少计算量 |
| 批量同步 | 分页拉取 + 批量 Upsert |

### 3.3 安全设计

| 威胁 | 防护措施 |
|------|----------|
| 租户数据泄漏 | GORM 插件自动注入 tenant_id 过滤 |
| 越权访问 | JWT 中间件 + 角色校验中间件 |
| 钉钉回调伪造 | 验签 + AES 解密 |

---

## 四、总结

Schedule Server 通过以下设计实现高效的排课考勤管理：

1. **多租户架构** - 一套系统服务多个机构，数据完全隔离
2. **钉钉深度集成** - 单点登录 + 组织同步 + 审批联动
3. **灵活的课程模型** - 支持复杂周次表达，全量替换保证一致性
4. **实时考勤计算** - 公式化计算应到人员，自动扣减请假
5. **可配置的作息** - 支持多模式、多时段，适应不同教学场景

系统架构清晰、边界明确，便于后续扩展打卡集成、消息推送等功能。
